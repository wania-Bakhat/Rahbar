# Failure analysis

`FAILURE_MODE` is a single-value switch shared by the API and indexer. It defaults to `off`;
valid fault values are `no_ocr`, `chunks_100`, `top_k_1`, `no_context_instruction`,
`no_superseded_filter`, and `temperature_1_2`. Set exactly one value at a time. Restore
`FAILURE_MODE=off` after each run.

The first two modes change the indexed data, so run the indexer with that mode and rebuild the
collection before evaluating. The other modes affect API query or generation behavior and need
an API restart. Keep the `--failure-mode` label equal to the mode actually active in the API.

`eval/golden.yaml` now contains the question mix and exact source/section annotations; scanned-document annotations still require confirmation after OCR. The failure protocol below describes which stage each switch changes. Symptoms, diagnoses from logs/metrics, saved scores and remedies must be filled with actual cluster runs; none are claimed as observed until the evidence files exist.

Run an ordinary healthy evaluation first, then each failure mode separately. For each row, save the JSON emitted by the evaluator and add the observed result to the run record below. Do not describe an expected failure as an observed result.

For the focused configuration experiments, `eval/failure-golden.yaml` contains the same five questions for each run: an ordinary attendance answer, current-versus-superseded version checks, an out-of-corpus abstention, and a prompt-injection probe. First save a healthy result with `--golden eval/failure-golden.yaml --out eval/failure-baseline.json --baseline eval/failure-baseline.json --update-baseline`; then pass that baseline to every mode run. This keeps each failure comparison on the same question set and avoids repeating the full 18-question generation run for every mode.

```bash
FAILURE_MODE=no_ocr .venv312/bin/python eval/run_eval.py --api http://<ingress> \
  --host rahbar.local --failure-mode no_ocr
```

Failure runs write to `eval/failure-results/<mode>.json` by default. Healthy runs write to
`eval/results.json`. A failure run cannot update the healthy baseline. The evaluator uses the
usual non-zero gate result for failures; the JSON result is still written before it exits.

## Additional failures observed in the healthy evaluation

These are evaluation failures discovered during review; they do not count as the assignment's four deliberately induced failure modes.

- **q10, answer generation:** the correct `1.21` clause was retrieved at rank 2, but the answer returned the nearby table-of-contents text and cited `1.20`. The failure persisted after rebuilding the API image and using a fresh cache namespace. A unit-level guard passes, but the live behavior did not change. Root cause remains unresolved; q10 stays a gate failure.
- **q07, retrieval:** the Student Handbook source contains `10. Training and Support` on page 60. Local extraction produces the exact heading as section metadata, but the live full run retrieved a table-of-contents/footer fragment and missed the annotated section. A source-plus-section filter and regression test have been added; deployment and live verification are pending because Docker/Minikube is unavailable.
- **q18, injection evaluation:** the service abstained safely, while retrieval missed the annotated relevant passage. This is recorded as a retrieval miss, not an unsafe answer.
